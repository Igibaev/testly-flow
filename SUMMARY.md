## Функционал

### 1. Загрузка тестов через единый MD-файл

Парсер (`MarkdownTestParser`) разбирает один файл, который содержит и вопросы, и ключ ответов:

- **Секция вопросов** — формат `**N. Текст вопроса?**` + варианты `- Буква) текст` (буквы кириллические: А, Б, В, Г и далее).
- **Секция ключа ответов** — после `---` под заголовком `## Ключ ответов`, markdown-таблица. Поддерживается **произвольное число повторяющихся пар «№ | Ответ» в одной строке** — парсер разбивает строку таблицы на ячейки и идёт по ним попарно, а не хардкодит фиксированное количество колонок.
- Автоматически связывает вопросы с ответами по номеру; при загрузке:
  - ошибка, если у вопроса нет ответа в ключе или ответ указывает на несуществующий вариант (со списком всех проблемных номеров сразу);
  - предупреждение (не блокирует загрузку), если в ключе есть номер без соответствующего вопроса;
  - название теста берётся из параметра `title` при загрузке, либо из первого заголовка `# ...` в файле.
- Покрыт 7 юнit-тестами: базовый разбор, несколько пар в строке, короткая последняя строка таблицы, отсутствующий ответ, лишний ответ в ключе, отсутствие вопросов, отсутствие секции ключа.

### 2. Подготовительные материалы

Список ссылок (`prep_links`), привязанный к конкретному тесту. Задаётся при загрузке теста или редактируется отдельно (`PUT /api/admin/tests/{id}/prep-links`). Отображается пользователю на стартовой странице теста перед началом прохождения.

### 3. Прохождение теста без авторизации

- Пользователь вводит имя, фамилию и команду на стартовой странице.
- При старте попытки backend фиксирует:
  - IP-адрес (с учётом `X-Forwarded-For`, иначе `remoteAddr`);
  - `User-Agent` из заголовка запроса.
- Все вопросы теста показываются на одной странице (single-page прохождение), выбор варианта — radio-кнопки.
- При отправке backend сам подсчитывает количество правильных ответов и процент (`ScoringCalculator`, округление до 2 знаков), сохраняет попытку целиком: кто, когда начал/закончил, откуда, по какому тесту, результат и детализация по каждому вопросу (`attempt_answers`).
- Повторное прохождение не ограничено — каждая попытка это отдельная запись.

### 4. Административная часть

Доступ к REST-админке закрыт паролем через заголовок `X-Admin-Password` (env `ADMIN_PASSWORD`, по умолчанию `admin`) — Spring-интерцептор на `/api/admin/**`. UI-админка спрашивает пароль один раз и держит признак в `VaadinSession` (сравнение пароля в постоянном времени).

Возможности:
- список всех загруженных тестов (с числом вопросов, числом попыток, датой создания);
- загрузка нового теста (multipart: MD-файл + опциональный `title` + опциональные подготовительные ссылки);
- редактирование подготовительных ссылок теста;
- список всех попыток прохождения с фильтрами по тесту и команде, пагинацией;
- просмотр детализации конкретной попытки (кто, откуда, статус, балл, ответ на каждый вопрос — свой/правильный/верно или нет).

### 5. Встроенный сбор метрик

Реализован вручную, без Prometheus/Grafana/Micrometer — агрегаты хранятся в отдельной таблице `metrics` (по тесту) и досчитываются "на лету" SQL-запросами к `attempts`:

- количество стартов теста и завершённых попыток (обновляются атомарно при старте/завершении попытки);
- количество незавершённых (`abandoned = starts − completed`);
- среднее время прохождения (`AVG(EXTRACT(EPOCH FROM finished_at − started_at))`, только по завершённым);
- распределение баллов по 5 корзинам: 0-20/21-40/41-60/61-80/81-100%;
- активность по командам: число попыток и средний балл на команду.

Доступны через `GET /api/admin/metrics?testId=` (без `testId` — агрегат по всем тестам сразу) и отображаются на дашборде во фронтенде простыми CSS-барами (без сторонних chart-библиотек).

## REST API

Единый формат ошибок: `{ "error": "...", "details": [...] }` через `@RestControllerAdvice`.

### Публичные

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/tests` | список тестов |
| GET | `/api/tests/{id}` | детали теста: описание, подготовительные ссылки, вопросы **без правильных ответов** |
| POST | `/api/tests/{id}/attempts/start` | начать попытку — `{firstName, lastName, team}` |
| POST | `/api/attempts/{attemptId}/submit` | завершить попытку — `{answers: [{questionId, selectedOption}]}`, возвращает балл и детализацию |

### Административные (заголовок `X-Admin-Password`)

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/admin/tests` | список тестов со статистикой |
| POST | `/api/admin/tests` | загрузка нового теста (multipart) |
| PUT | `/api/admin/tests/{id}/prep-links` | обновление подготовительных ссылок |
| GET | `/api/admin/attempts?testId=&team=&page=&size=` | список попыток с фильтрами |
| GET | `/api/admin/attempts/{id}` | детализация попытки |
| GET | `/api/admin/metrics?testId=` | метрики по тесту / по всем тестам |
| GET | `/api/admin/auth/check` | проверка admin-пароля (используется фронтом при входе) |

## Схема базы данных

`tests` → `questions` → `question_options`; `tests` → `prep_links`; `tests` → `attempts` → `attempt_answers`; `tests` → `metrics` (1:1 агрегаты по тесту).

Правильный ответ хранится непосредственно в `questions.correct_option` (без отдельной таблицы `answer_keys` — она была бы избыточным дублированием этого поля). Данные PostgreSQL сохраняются в именованном Docker-volume `pgdata` и переживают перезапуск контейнеров.

Миграции (Flyway):
- `V1__init.sql` — базовая схема (7 таблиц, FK, индексы, уникальные ограничения).
- `V2__fix_option_column_types.sql` — исправление типов колонок `correct_option`/`option_letter`/`selected_option` с `CHAR(1)` (Postgres `bpchar`) на `VARCHAR(1)`, чтобы соответствовать тому, что ожидает Hibernate для `String`-полей (иначе падал `Schema-validation` при старте).

## Frontend — страницы

**Публичная часть:**
- `/` — витрина категорий и форма старта;
- `/attempt/:id` — пошаговое прохождение;
- `/attempt/:id/result` — мотивирующий результат без правильных вариантов.

**Админ-раздел (`/admin`):**
- вход по паролю;
- `categories` — категории и подготовительные ссылки;
- `tests` — загрузка MD-файлов;
- `attempts` / `attempts/:id` — попытки и детализация;
- `employees` / карточка сотрудника;
- `metrics` — дашборд.

## Инфраструктура

- `docker-compose.yml`: два сервиса — `postgres` (healthcheck, volume `pgdata`) и `app` (ждёт готовности БД, порт 8080). Поднимается одной командой `docker-compose up --build`.
- `.env.example` — `POSTGRES_DB/USER/PASSWORD`, `ADMIN_PASSWORD`.
- Dockerfile — многостадийная сборка `mvn -Pproduction` → JRE.

## Известные ограничения / что не проверялось в этой сессии

- Полный `docker-compose up` end-to-end не прогонялся (в среде нет Docker daemon). Проверено: `mvn test`. Реальный сквозной прогон стоит сделать перед продакшен-использованием.
- UI stateful: больше одного инстанса `app` требуют sticky sessions. Таймаут HTTP-сессии — 4 часа.
- Тайминги из UI считает сервер, поэтому попытки через UI почти не получают `timing_suspicious`. Проверка по REST-клиентам сохранена.
- Нет rate limiting / anti-spam защиты публичных эндпоинтов.
- Нет ограничения по времени на прохождение теста (осознанное решение).
