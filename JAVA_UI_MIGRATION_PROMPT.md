# Промт для переписывания фронтенда на Java: один модуль вместо двух

Ты — senior Java-инженер. Твоя задача — **переписать фронтенд проекта «Платформа для тестирования знаний» с React на Java** и **свести репозиторий с двух модулей (`backend/` + `frontend/`) к одному Maven-модулю**, в котором вся серверная логика и весь UI написаны на Java. Работай в существующем репозитории, а не с нуля: бизнес-логика, схема БД, парсер MD-файлов и REST API уже написаны и покрыты тестами — их нужно сохранить, а не переизобрести.

Не оставляй TODO, заглушек и «здесь будет UI». Итог — работающее приложение, которое поднимается одной командой `docker-compose up --build`, отдаёт весь UI и API с одного порта, и на котором `mvn test` зелёный.

## 2. Технологический выбор (строго, не обсуждается)

- **UI — Vaadin Flow 24.3.x** (`vaadin-bom` в `dependencyManagement`, зависимость `vaadin-spring-boot-starter`). Причина выбора: это единственный зрелый способ описывать компонентный UI, состояние и обработчики событий целиком на Java, без шаблонов и без ручного JS. Vaadin 24.3 построен на Spring Boot 3.2.x — совпадает с текущей версией проекта (3.2.5), поэтому Spring Boot поднимать не нужно.
- **Java 17**, **Spring Boot 3.2.5**, **Maven** — как сейчас.
- Всё остальное без изменений: Spring Web, Spring Data JPA, Bean Validation, Flyway, PostgreSQL 16, Docker + docker-compose.

Про версии: ядро Vaadin Flow распространяется под Apache 2.0, но бесплатные обновления безопасности выпускаются только для свежих минорных версий, а 24.3 из этого окна уже вышла. Это осознанный компромисс ради того, чтобы не поднимать Spring Boot в рамках этой миграции. Если нужны свежие патчи — берётся более новая минорная Vaadin 24.x вместе с той версией Spring Boot, которая указана в её release notes как baseline (например, 24.8 требует Spring Boot 3.5), и тогда апгрейд Spring Boot делается **отдельным коммитом до** начала работы над UI, с прогоном `mvn test`. Смешивать несовместимую пару Vaadin/Spring Boot нельзя — приложение падает в рантайме.

## 3. Инварианты, которые нельзя нарушить

Это то, что проверяется тестами и составляет смысл продукта. После миграции всё это должно быть по-прежнему верно.

1. **Правильный ответ никогда не попадает к сотруднику.** Ни на экране прохождения, ни на экране результата — ни в разметке, ни в атрибутах, ни в DOM-данных компонентов. Экран результата показывает «твой ответ» и факт ошибки, но не верный вариант. В Vaadin состояние живёт на сервере, поэтому достаточно не рендерить эти данные — но проверь это тестом (§10) и не используй в экранах сотрудника DTO `AnswerDetailDto`/`AdminAttemptDetailDto`, у которых есть `correctOption`. Для сотрудника — только `PublicAnswerDetailDto`.
2. **Состав попытки фиксируется на старте** и не пересобирается при перезагрузке страницы, пока `status = IN_PROGRESS`. Источник истины — `AttemptService.getAttemptState(attemptId)`.
3. **Обращение к завершённой попытке** через экран прохождения — это ошибка «Эта попытка уже завершена» (сейчас распознаётся по HTTP 409; после миграции — по `ConflictException` из сервиса).
4. **Автосохранение каждого ответа** сразу при выборе варианта, через `AttemptService.updateAnswer(...)`. Ответ можно снять повторным нажатием на выбранный вариант.
5. **Тайминги — абсолютное накопленное значение по вопросу**, а не дельта; повторная отправка не удваивает время. Время не тикает, когда вкладка скрыта. Санитизация значений и флаг `timing_suspicious` остаются в сервисе.
6. **Админка закрыта паролем** из `ADMIN_PASSWORD`, ввод один раз на сессию. REST-админка по-прежнему требует заголовок `X-Admin-Password`.
7. **IP и User-Agent** фиксируются на старте попытки, с учётом `X-Forwarded-For`.
8. **Визуальный дизайн сохраняется**: те же токены (`tokens.css`), та же типографика, та же светлая/тёмная тема по `prefers-color-scheme` и атрибуту `data-theme`, тот же принцип «один вопрос на экране, минимум тревожности, прогресс вместо таймера обратного отсчёта».

Источник требований — существующие `HomePage.jsx`, `AttemptPage.jsx`, `ResultPage.jsx`. Поведение должно совпадать, включая тексты на русском и формы множественного числа. ### 7.1. `HomeView` (`/`)

- Заголовок «Проверь себя», лид-абзац о том, как собирается тест.
- Карточки категорий из `CategoryService.listPublic()`: название, описание, «N вопросов в пуле», подготовительные ссылки (`target=_blank`, `rel=noreferrer`), цвет-акцент категории через CSS-переменную `--cat-accent`.
- Оценка размера теста («Тест соберёт 30–45 вопросов из 3 блоков»): сейчас фронт считает её по зашитым константам `SAMPLE_MIN = 10 / SAMPLE_MAX = 15`, что расходится с настройками `testly.sampling.*` и переопределениями `categories.questions_min/max`. **Исправь при переносе**: считай оценку на сервере из `TestlyProperties` и полей категории. Если по категории заданы свои `questionsMin/Max` — учитывай их.
- Форма «Начать тест»: имя, фамилия, команда; все три обязательны, пустые/из пробелов — ошибка «Заполни имя, фамилию и команду» без обращения к серверу. Кнопка «Пройти тест» → `AttemptService.startAttempt(...)` → переход на `/attempt/{id}`.
- Блок формы не показывается, если ни в одной категории нет вопросов; вместо этого — «Пока нет ни одного блока с вопросами. Загрузите вопросы в админ-панели.»
- IP и User-Agent для `startAttempt`: бери из `VaadinRequest`/`VaadinSession` (`getRemoteAddr()`, заголовок `User-Agent`), с учётом `X-Forwarded-For` — вынеси эту логику в `ui/support/ClientInfoResolver`, чтобы правило было в одном месте и совпадало с тем, что делает контроллер.

### 7.2. `AttemptView` (`/attempt/:attemptId`)

Самый сложный экран. Требования:

- Состояние берётся из `AttemptService.getAttemptState(attemptId)`; `ConflictException` (попытка завершена) → сообщение «Эта попытка уже завершена.» и кнопка «На главную»; прочие ошибки — «Не удалось загрузить попытку: …».
- Один вопрос на экране: категория-плашка с цветом, «Вопрос N из M», прогресс-бар по числу **отвеченных** вопросов с `role="progressbar"` и корректными `aria-valuenow/min/max`, подпись «Отвечено N из M».
- Варианты ответа — карточки-кнопки с буквой и текстом, `aria-pressed` на выбранной. Клик по выбранному варианту снимает ответ.
- Каждое изменение ответа немедленно уходит в `AttemptService.updateAnswer(...)` вместе с накопленным временем. Сбой сохранения не должен ломать прохождение: покажи неблокирующее уведомление и продолжай — финальная синхронизация на `submit` дошлёт всё.
- Навигация: «← Назад», «Далее →» (крайние кнопки задизейблены), боковой навигатор со всеми вопросами, сгруппированными по категориям, с четырьмя состояниями ячейки (`answered`, `skipped` — посещён без ответа, `unvisited`, `current`), легендой и кнопкой «Все вопросы» / «Скрыть список вопросов» для мобильной раскладки. Переход на любой вопрос — по клику.
- Горячие клавиши: `→`/`Enter` — следующий вопрос, `←` — предыдущий, `1..6` и `А..Е` (плюс латинские `A..F`) — выбор варианта по порядковому номеру. Реализуй через `Shortcuts`/`ShortcutRegistration` на Java. Клавиши не должны срабатывать, когда открыт диалог завершения или фокус в поле ввода.
- Кнопка «Завершить тест» открывает модальное окно: если есть неотвеченные — перечисли их номера, дай кнопки «Вернуться к первому пропущенному» и «Всё равно завершить»; если все отвечены — «Продолжить» и «Завершить». Отправка — `AttemptService.submitAttempt(...)`, затем переход на `/attempt/{id}/result`.
- Доступность: скрытая live-область, объявляющая «Вопрос N из M» при смене вопроса (аналог нынешнего `aria-live` div), осмысленные `title`/`aria-label` у ячеек навигатора.
- Перезагрузка страницы в середине прохождения возвращает тот же состав вопросов и сохранённые ответы (это уже гарантирует сервис), а накопленное время подхватывается из сохранённых `attempt_answers` (§8).

### 7.3. `ResultView` (`/attempt/:attemptId/result`)

- Показывает `SubmitAttemptResponse`: подпись уровня (`GROWTH` → «Точка роста», `SOLID` → «Уверенная база», `STRONG` → «Сильный результат», `EXEMPLARY` → «Отличный результат»), `headline`, «N из M», `message`.
- Блок «На что посмотреть» — `focusAreas` с процентом верных, числом ошибок и подготовительными ссылками категории.
- «Разбор ошибок» — только неверные ответы: категория, текст вопроса, «Твой ответ: X» (или «— не выбран»). **Правильный вариант не показывается и не передаётся в браузер.** Если ошибок нет — «Ошибок нет.»
- Кнопка «Пройти ещё раз» → `/`.
- Результат сейчас передаётся через router state и теряется при перезагрузке. Сохрани это поведение, но реализуй по-серверному: положи `SubmitAttemptResponse` в `VaadinSession` под ключом вида `result:{attemptId}` и читай оттуда. Если значения нет (прямой переход по ссылке, новая сессия) — покажи нынешний фолбэк «Результат недоступен — возможно, страница была перезагружена.» и кнопку «На главную». Не собирай результат заново из админских сервисов: там есть правильные ответы.

## 8. Шаг 5 — тайминги без клиентского таймера

Сейчас время считает React-хук `useQuestionTimer` и присылает накопленное значение на сервер. После миграции состояние живёт на сервере — перенеси таймер в Java, сохранив смысл метрики.

1. `ui/support/QuestionTimer` — объект уровня view (по одному на открытую попытку): `Map<Long questionId, long accumulatedMs>`, идентификатор активного вопроса, `Instant activeSince`. Метод `setActiveQuestion(id)` дописывает накопленное для предыдущего вопроса и начинает отсчёт нового; `accumulatedMs(id)` возвращает накопленное с учётом текущего незакрытого интервала.
2. Инициализируй накопленные значения из уже сохранённых ответов попытки (`AttemptStateDto.answers[].timeSpentMs`) — тогда перезагрузка страницы не сбрасывает время.
3. Время **не тикает, когда вкладка скрыта**. Это единственное, что нельзя узнать на сервере, поэтому разреши один микро-мостик: `Page.executeJs` регистрирует `document.addEventListener('visibilitychange', …)`, который вызывает `@ClientCallable`-метод view (`visibilityChanged(boolean hidden)`), а тот дёргает `pause()`/`resume()` таймера. До 10 строк JS, встроенных строкой в Java, с комментарием, почему без них нельзя.
4. Флашь накопленное время в БД в тех же точках, что и сейчас: при выборе/снятии ответа, при переходе между вопросами, при открытии диалога завершения и при `submit`. Всё — через `AttemptService.updateAnswer(...)`/`submitAttempt(...)`, чтобы санитизация и `timing_suspicious` остались единственной реализацией в сервисе.
5. Закрытие вкладки: `beforeunload` больше не нужен. Повесь `UI.addDetachListener` и дофлашь время, **но не засчитывай интервал до момента отсоединения** — иначе в метрику попадёт время, пока сессия просто ждала таймаута. Засчитывай не позже последней подтверждённой активности клиента (последний запрос/heartbeat). Опиши это правило в README.
6. Побочный эффект, который надо зафиксировать в README: тайминги из UI теперь считает сервер, поэтому попытки, пройденные через UI, практически не будут помечаться `timing_suspicious`. Сама проверка и флаг остаются — `PUT /api/attempts/{id}/answers/{questionId}` по-прежнему принимает время от произвольного клиента, и доверять ему нельзя.

Сквозной сценарий вручную: загрузка `sample-test.md` в админке в новую категорию → на главной видна категория с числом вопросов и оценкой размера теста → старт попытки → пошаговое прохождение (клик, клавиатура, навигатор, снятие ответа) → перезагрузка страницы посреди попытки не меняет состав вопросов и сохранённые ответы → завершение с пропущенными вопросами через диалог → экран результата с уровнем, «На что посмотреть» и разбором ошибок без правильных ответов.

## 15. Подводные камни (знай заранее)

1. **Vaadin + Spring MVC на одном порту.** Проверяй REST сразу после подключения Vaadin, а не в конце: это самая частая поломка такой миграции.
2. **Коммерческие компоненты Vaadin** валят сборку требованием лицензии. Не используй ничего из Pro-набора (см. §2.3).
3. **Тема Lumo против дизайна проекта.** Не смешивай Lumo-компоненты с портированным CSS без явного маппинга токенов, иначе экран сотрудника поедет по типографике и отступам.
4. **Горячие клавиши и поля ввода.** Vaadin-шорткаты по умолчанию глобальны — ограничь их областью view и отключай, когда открыт диалог или фокус в текстовом поле.
5. **Долгие попытки и таймаут сессии.** Дефолтные 30 минут убьют попытку на середине — см. §10.1.
6. **Тайминг при закрытии вкладки.** Без правила «не позже последней активности» время последнего вопроса раздуется на весь таймаут сессии.
7. **Кириллица в route-параметрах** карточки сотрудника: проверь кодирование/декодирование, иначе ссылка из списка сотрудников будет открывать пустую карточку.
8. **Оценка размера теста на главной** сейчас зашита константами и врёт при изменённых настройках — не переноси баг, посчитай на сервере (§7.1).
9. **`ConflictException`/`NotFoundException`** больше не превращаются в HTTP-коды автоматически: `GlobalExceptionHandler` работает только для REST. В UI ловите их явно и показывайте те же тексты, что показывал фронт по кодам 409/404.

## 16. Порядок работы и формат сдачи

Иди шагами, каждый — отдельный компилируемый коммит с зелёным `mvn test`:

1. Слияние модулей и Docker/compose/README-инфраструктура (без UI-кода) — §4.
2. Каркас Vaadin, тема, маршруты, `MainLayout` — §5, §6.
3. Экраны сотрудника: `HomeView` → `AttemptView` → `ResultView`, вместе с `QuestionTimer` — §7, §8.
4. Админка: гейт, layout, семь экранов — §9.
5. Настройки сессий/эксплуатации и smoke-тест REST — §10.
6. UI-тесты — §11.
7. README и финальная сверка по §14.

Перед реализацией каждого шага коротко покажи план: какие файлы создаёшь/удаляешь и какие решения принимаешь. После шага 3 и шага 4 обязательно прогони сквозной сценарий из §14.4 вручную. В конце приложи список удалённых файлов и список новых Java-классов с одной строкой назначения у каждого.

## 17. Приложение: если Vaadin недопустим

Использовать только при явном запрете Vaadin (например, из-за политики лицензирования на будущие мажорные версии). Тогда: Spring Boot + Thymeleaf для серверного рендеринга и htmx для частичных обновлений; вся логика экранов — в Java-контроллерах, шаблоны — тонкие. Требования §1 (один модуль), §3 (инварианты), §12–§14 (документация, карта переноса, приёмка) остаются в силе. Цена такого варианта: HTML-шаблоны и атрибуты htmx — это уже не «всё на Java», плюс таймер на вопрос и горячие клавиши придётся писать на JS руками. Поэтому по умолчанию — Vaadin.
