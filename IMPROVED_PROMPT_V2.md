## 1. Категории вопросов и новая сборка теста

### 1.1. Модель данных

Сейчас «тест» = один загруженный MD-файл. Это меняется: **загруженный файл — это пул вопросов внутри категории, а не самостоятельный тест**. Тест собирается динамически на старте попытки.

Новая миграция `V3__categories.sql`:

- **categories** — `id BIGSERIAL PK`, `name VARCHAR(200) NOT NULL UNIQUE`, `slug VARCHAR(200) NOT NULL UNIQUE` (генерируется из name транслитерацией), `description TEXT`, `color VARCHAR(16)` (HEX для UI-акцента, необязателен), `sort_order INTEGER NOT NULL DEFAULT 0`, `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`.
- **questions** получает `category_id BIGINT NOT NULL REFERENCES categories(id) ON DELETE CASCADE` + индекс `idx_questions_category_id`.
- Уникальность `questions(test_id, number)` больше не годится как единственная — номер уникален в пределах загруженного файла, а не категории. Замени на `UNIQUE (test_id, number)` (остаётся) и добавь `questions.display_number` — номер, который видит сотрудник, присваивается **на лету при сборке попытки** (1..N), в БД не хранится.
- **tests** остаётся как «партия загрузки» (upload batch): `category_id` (FK, NOT NULL), `title` (название файла/партии), `created_at`. В UI сотрудника таблица `tests` больше не фигурирует вообще — это админская сущность.

Про старые данные: **обратная совместимость не требуется**. Миграция может очистить `tests / questions / question_options / attempts / attempt_answers / metrics` (`TRUNCATE ... CASCADE`) перед добавлением NOT NULL-колонок. Явно напиши об этом в README и в комментарии к миграции — деструктивная миграция должна быть осознанной, а не сюрпризом.

### 1.2. Загрузка файла — категория обязательна

`POST /api/admin/tests` (multipart) получает **взаимоисключающую пару** параметров:
- `categoryId` (Long) — добавить вопросы файла в существующую категорию, **или**
- `newCategoryName` (String) + опционально `newCategoryDescription`, `newCategoryColor` — создать новую категорию и привязать к ней.

Правила:
- Не передано ни одного — `400` с внятным сообщением («Укажите категорию: выберите существующую или создайте новую»).
- Переданы оба — `400`.
- `newCategoryName` дублирует существующую категорию (сравнение без учёта регистра и крайних пробелов) — `400` с подсказкой использовать `categoryId` этой категории.
- Успех — в ответе `UploadTestResponse` дополнительно `{categoryId, categoryName, categoryCreated: bool, questionsAdded: int}`.

Новые админские эндпоинты:
- `GET /api/admin/categories` — `[{id, name, slug, description, color, questionCount, testCount, sortOrder}]`.
- `POST /api/admin/categories` — создать категорию без загрузки файла.
- `PUT /api/admin/categories/{id}` — переименовать / изменить описание, цвет, порядок.
- `DELETE /api/admin/categories/{id}` — только если в ней нет вопросов, иначе `409` с числом вопросов.

Публичный `GET /api/categories` — `[{id, name, description, color, questionCount}]` для витрины перед стартом (сотрудник видит, из каких блоков будет тест).

Формат MD-файла **не меняется** — категория задаётся только параметром загрузки. В форме загрузки в админке: селект существующих категорий + переключатель «Создать новую», с обязательной валидацией на клиенте и на сервере.

### 1.3. Сборка теста на старте попытки

Старый флоу «пройти конкретный тест `/test/:id`» **убирается полностью**. Вместо него — одна кнопка «Пройти тест», собирающая комплексную сессию.

Настройки выборки — в `application.yml` + env, с дефолтами:
```yaml
testly:
  sampling:
    questions-per-category-min: 10   # TESTLY_QUESTIONS_PER_CATEGORY_MIN
    questions-per-category-max: 15   # TESTLY_QUESTIONS_PER_CATEGORY_MAX
    shuffle-questions: true          # перемешивать ли порядок вопросов в собранной попытке
```
Плюс возможность переопределить их из админки (таблица настроек или редактируемые поля категории — реши сам, но опиши решение в README; если через категорию, то поля `questions_min` / `questions_max` в `categories` с fallback на глобальные).

Алгоритм `POST /api/attempts/start` (тело `{firstName, lastName, team}`):
1. Взять все категории, где `questionCount > 0`.
2. Для каждой: `n = random(min, max)` включительно; если вопросов в категории меньше `n` — берём **все** имеющиеся (не падаем, не дублируем).
3. Случайная выборка без повторов — на стороне SQL (`ORDER BY random() LIMIT n`), не вытаскивая весь пул в память.
4. Если категорий с вопросами нет — `409` «Тест ещё не наполнен вопросами».
5. Создать `attempt` и **зафиксировать состав**: строки в `attempt_answers` создаются сразу на старте, по одной на выбранный вопрос, с `selected_option = NULL`, `is_correct = false` и `display_number` (порядковый номер в этой попытке). Это критично: состав попытки не должен пересобираться при перезагрузке страницы.
6. Порядок: если `shuffle-questions=true` — вопросы перемешиваются глобально; если false — идут блоками по категориям в порядке `sort_order`. Дефолт — **false** (блоками), так сотруднику проще держать контекст, а метрики по блокам читаются честнее.
7. Ответ: `{attemptId, startedAt, questions: [{questionId, displayNumber, categoryId, categoryName, text, options: [{letter, text}]}], totalQuestions, categoriesCount}` — **без правильных ответов**.

Дополнительно: `GET /api/attempts/{attemptId}` — вернуть состав и уже сохранённые ответы, чтобы попытка переживала перезагрузку вкладки. Отдавать только для `status=IN_PROGRESS`; для завершённой — `409`.

## 2. Пошаговое прохождение: один вопрос за раз

### 2.1. Поведение фронта

Маршрут `/attempt/:attemptId` (страница прохождения) вместо `/test/:id/run`.

- На экране **ровно один вопрос**: номер («Вопрос 7 из 42»), плашка категории, текст, варианты ответа.
- Навигация: «Назад» / «Далее», плюс **навигатор по всем вопросам** — сетка кнопок-номеров сбоку (десктоп) или сворачиваемая панель сверху (мобайл). Клик по номеру — мгновенный переход к любому вопросу.
- Состояния в навигаторе, различимые не только цветом (обязательно — иконка/форма/подчёркивание): `отвечен` · `пропущен, посещён` · `не посещён` · `текущий`. Никакой информации о правильности — сотрудник её на этом этапе не видит вообще.
- Разделители блоков: в навигаторе вопросы сгруппированы по категориям с подписью категории.
- Прогресс: полоса «отвечено N из M» + сколько осталось. Прогресс считается по отвеченным, а не по посещённым.
- Кнопка «Завершить тест» доступна всегда, но при неотвеченных вопросах показывает подтверждение со списком их номеров и кнопкой «Вернуться к первому пропущенному».
- Клавиатура: `←`/`→` — переход, `1..6` или `А/Б/В/Г/Д/Е` — выбор варианта, `Enter` — далее. Фокус-стили обязательны.
- Выбор ответа **не** перематывает на следующий вопрос автоматически — это раздражает при исправлении.

### 2.2. Автосохранение и API ответов

Каждый выбор варианта немедленно уходит на backend — попытка не должна теряться при закрытии вкладки.

Новый эндпоинт: `PUT /api/attempts/{attemptId}/answers/{questionId}`
```json
{ "selectedOption": "Б", "timeSpentMs": 14200 }
```
- Идемпотентен, вызывается при каждой смене ответа (в т.ч. при смене уже выбранного).
- `selectedOption: null` — снять ответ.
- `timeSpentMs` — **накопленное** время по этому вопросу, измеренное на клиенте (см. 2.3). Backend прибавляет дельту к сохранённому значению? Нет — принимай **абсолютное накопленное** значение и перезаписывай им поле: так повторная отправка не удваивает время.
- Валидации: попытка существует и `IN_PROGRESS` (иначе `409`), `questionId` входит в состав попытки (иначе `400`), `selectedOption` — одна из букв вариантов этого вопроса (иначе `400`), `timeSpentMs >= 0` и не больше разумного потолка (например, 6 часов — обрезай сверху, не падай).
- Ответ: `204 No Content`. `is_correct` пересчитывается на сервере и хранится, но **не возвращается**.

`POST /api/attempts/{attemptId}/submit` упрощается: тело `{ answers: [...], timings: [{questionId, timeSpentMs}] }` остаётся поддерживаемым как «финальная синхронизация» (на случай, если часть автосейвов не долетела), но состав попытки берётся из БД, а не из тела. Лишние `questionId` в теле игнорируются с предупреждением в логе, а не ошибкой.

Отдельно отправляй «финальный флаш» тайминга текущего вопроса непосредственно перед submit — иначе время последнего вопроса потеряется.

### 2.3. Как измеряется время на вопрос

На клиенте:
- Таймер стартует, когда вопрос становится видимым, и останавливается при уходе с него (переход, submit, закрытие вкладки).
- `document.visibilitychange`: при уходе со вкладки таймер **паузится**, при возврате — продолжается. Иначе «ушёл на обед» превратит метрику в мусор.
- Накопленное время хранится в `Map<questionId, ms>` и отправляется вместе с ответом и при уходе с вопроса (`sendBeacon` / `keepalive: true` на `beforeunload` — по возможности).
- Возвраты к вопросу суммируются: три захода по 5 секунд — это 15 секунд на вопросе.

На сервере это **не источник истины о честности**, а метрика — но санитизируй её: отрицательные значения → 0, значения выше потолка → потолок, сумма таймингов не может превышать `finished_at - started_at` более чем на 10% (иначе логируй аномалию и помечай попытку флагом `timing_suspicious`).

### 2.4. Миграция под тайминги

`V4__question_timings.sql`:
- `attempt_answers`: `+ display_number INTEGER`, `+ time_spent_ms BIGINT NOT NULL DEFAULT 0`, `+ answered_at TIMESTAMPTZ`, `+ visits_count INTEGER NOT NULL DEFAULT 0`.
- `attempts`: `+ timing_suspicious BOOLEAN NOT NULL DEFAULT false`.
- Индексы: `attempt_answers(question_id)`, `attempt_answers(attempt_id, display_number)`.

## 3. Метрики: время по вопросам и по блокам

Расширь `GET /api/admin/metrics`. Существующие поля (`startsCount`, `completedCount`, `abandonedCount`, `averageDurationSeconds`, `scoreDistribution`, `teamActivity`) остаются. Параметры: `categoryId` (опционально), `from` / `to` (опционально, по `started_at`).

Новая форма ответа — добавляются блоки:

```json
{
  "questionTiming": {
    "averageTimePerQuestionSeconds": 27.4,
    "medianTimePerQuestionSeconds": 21.0,
    "slowestQuestions": [
      { "questionId": 42, "number": 7, "text": "…", "categoryId": 3, "categoryName": "Флоу гашения",
        "avgTimeSeconds": 96.2, "medianTimeSeconds": 88.0, "samplesCount": 54, "correctRate": 31.5 }
    ],
    "fastestQuestions": [ { "...": "та же структура" } ]
  },
  "categoryMetrics": [
    {
      "categoryId": 3, "categoryName": "Флоу гашения", "color": "#c2410c",
      "questionsServed": 540, "attemptsCovered": 42,
      "avgTimePerQuestionSeconds": 41.8, "medianTimePerQuestionSeconds": 35.0,
      "avgTimePerAttemptSeconds": 502.0,
      "correctRate": 58.3,
      "slowestQuestion": { "questionId": 42, "number": 7, "avgTimeSeconds": 96.2 },
      "fastestQuestion": { "questionId": 51, "number": 16, "avgTimeSeconds": 8.1 }
    }
  ],
  "categoryRanking": {
    "slowestCategories": ["Флоу гашения", "…"],
    "fastestCategories": ["…"],
    "weakestCategories": ["…"]
  }
}
```

Требования к расчёту:
- Считается **только по завершённым попыткам** (`status = COMPLETED`) и только по ответам с `time_spent_ms > 0`. Незавершённые попытки искажают средние.
- `slowestQuestions` / `fastestQuestions` — топ-10 каждый, сортировка по среднему времени. **Порог минимума наблюдений**: вопрос попадает в рейтинг только при `samplesCount >= 5` (значение вынеси в конфиг `testly.metrics.min-samples`) — иначе один медленный сотрудник сделает вопрос «самым сложным». Если данных не хватило ни одному вопросу — верни пустые списки и на дашборде покажи «Недостаточно данных: нужно минимум N ответов на вопрос».
- Медиана — через `percentile_cont(0.5) WITHIN GROUP (ORDER BY time_spent_ms)` в PostgreSQL. Средние без медианы врут на выбросах, поэтому нужны обе.
- Всё считается SQL-агрегатами (`GROUP BY`), а не выгрузкой строк в Java и подсчётом в цикле.
- `correctRate` рядом со временем — обязателен: «долго и правильно» (сложный, но освоенный) и «долго и неправильно» (провал в знаниях) — это разные выводы, и дашборд должен позволять их различать.
- Попытки с `timing_suspicious = true` исключаются из таймингов, но остаются в баллах. В ответе — поле `excludedSuspiciousAttempts`.

Дашборд (`AdminMetricsPage`) без chart-библиотек:
- Секция «Время на вопрос»: две таблицы — самые долгие и самые быстрые вопросы, с колонками «время (сред./медиана)», «% верных», «наблюдений», плашкой категории и полосой-баром на CSS.
- Секция «По блокам»: карточки категорий с горизонтальными барами по времени и по `correctRate`, отсортированные по «проблемности».
- Каждая цифра снабжена короткой подписью, что она значит. Дашборд, который надо расшифровывать, не используют.
- Фильтр по категории и по датам — в шапке секции.

Детализация попытки (`GET /api/admin/attempts/{id}`) тоже дополняется: у каждого ответа — `timeSpentMs` и категория, плюс сводка «самый долгий вопрос в этой попытке» и разбивка времени по блокам.

## 4. Мотивирующая обратная связь после теста

После submit сотрудник видит не сухой процент, а осмысленный отклик. Тон — **поддерживающий и конкретный, без снисходительности и без фальшивого восторга**. Формулировки на «ты», как коллега коллеге.

Backend в `SubmitAttemptResponse` добавляет:
```json
{
  "resultTier": "GROWTH | SOLID | STRONG | EXEMPLARY",
  "headline": "…",
  "message": "…",
  "focusAreas": [ { "categoryId": 3, "categoryName": "Флоу гашения", "correctRate": 42.0, "wrongCount": 7 } ]
}
```

Пороги (вынеси в конфиг, чтобы правились без пересборки):
- `< 50%` → **GROWTH**: «Теперь ты знаешь, что подтянуть». Смысл: провал — это не приговор, а карта пробелов. Например: *«Это нормальный результат для начала. Главное — теперь у тебя есть точная карта: вот эти блоки стоит разобрать, и следующая попытка будет другой».* Никакого «не расстраивайся» — это подразумевает, что есть из-за чего расстраиваться.
- `50–74%` → **SOLID**: база есть, есть куда расти. *«База уверенная. Два блока ниже остальных — добери их, и результат станет сильным».*
- `75–89%` → **STRONG**: *«Сильный результат. Ты хорошо держишь материал».*
- `>= 90%` → **EXEMPLARY**: *«Отличный результат — на таких, как ты, команда и держится. Коллеги могут приходить к тебе с вопросами».*

Правила формирования:
- `focusAreas` — категории с `correctRate` ниже среднего по этой попытке, максимум 3, отсортированы по возрастанию `correctRate`. Именно они превращают абстрактную мотивацию в план действий.
- Рядом с каждой слабой категорией — **подготовительные ссылки** этой категории (`prep_links` переезжают с `test_id` на `category_id` в миграции `V3`). Это замыкает петлю: «вот пробел → вот материал».
- Не менее 2–3 вариантов текста на каждый tier, выбор случайный — одинаковая фраза при каждом прохождении обесценивается.
- Тексты — в отдельном ресурсном файле (`feedback-messages.yml` или константы в одном классе), а не разбросаны по коду. Их будут править не программисты.
- На фронте: заголовок tier, крупный балл, сообщение, блок «На что посмотреть» с категориями и ссылками, кнопка «Пройти ещё раз».
- Никаких конфетти и звуков. Внешняя награда за результат теста снижает внутреннюю мотивацию учиться — а нам нужна именно она.

## 5. Убрать подсветку верно отвеченных вопросов

**Допущение** (если оно неверно — скажи до реализации): речь про страницу результата, где сейчас каждый ответ помечается зелёным `badge-correct` / красным `badge-incorrect`.

Что делать:
- Верно отвеченные вопросы **не подсвечиваются вообще**: нет зелёного бейджа, нет зелёной рамки, нет галочки. Нейтральный фон, как у обычной строки.
- В детализации по умолчанию показываются **только ошибки** — это фокус внимания на том, что требует работы. Верные ответы доступны через сворачиваемый блок «Показать все ответы (N)», свёрнутый по умолчанию.
- Для ошибочного ответа: текст вопроса, что было выбрано, что верно, категория. Стиль сдержанный — тонкая полоса-акцент слева, не заливка. Красная заливка списка вызывает защитную реакцию и мешает читать разбор.
- В процессе прохождения (`/attempt/:id`) правильность не показывается **ни в каком виде** — ни в навигаторе, ни у вопроса.
- Метрики и `is_correct` в БД, само собой, остаются — меняется только представление.

## 6. Редизайн UI: принципы и конкретика

Цель — не «сделать красиво», а снизить тревожность, удержать внимание и сохранить мотивацию учиться. Ниже — принципы с обоснованием и тем, что конкретно из них следует. Реализация — обычный CSS (можно CSS-переменные и модули), без UI-китов.

### 6.1. Принципы и что из них следует

**Когнитивная нагрузка (Sweller).** Рабочая память вмещает единицы элементов; всё, что не относится к текущему вопросу, конкурирует с ним за ресурс. → Один вопрос на экране (п. 2) — это уже реализация принципа. Дополнительно: во время прохождения шапка сворачивается до минимума, навигатор визуально тише вопроса, никаких баннеров и посторонних блоков. Ширина строки вопроса — 60–75 символов.

**Тревожность снижает результат.** Тест ассоциируется с оценкой и наказанием; тревога съедает ту же рабочую память. → Убираем всё, что читается как надзор: никакого обратного таймера на экране (время меряется, но не показывается — это ключевое), никакого красного до завершения, формулировки нейтральные («Вопрос 7 из 42», а не «Осталось 35»). Палитра спокойная, без сигнальных цветов в основном интерфейсе.

**Прогресс мотивирует сильнее, чем цель.** Видимое продвижение подпитывает вовлечённость. → Полоса прогресса заполняется по отвеченным вопросам, плавная анимация 200–300 мс. Завершённый блок категории отмечается в навигаторе. Показывай «отвечено 12 из 42», а не только процент — счётчик конкретнее.

**Контроль снижает сопротивление (self-determination theory).** Возможность вернуться и исправить убирает страх «ошибся навсегда». → Свободная навигация между вопросами, изменение ответа без ограничений, явная кнопка «Вернуться к пропущенным», подтверждение перед завершением.

**Ошибка как информация, а не как приговор.** Обратная связь, ориентированная на процесс, поддерживает установку на рост (Dweck); оценочная — фиксирует. → П. 4 и 5: убрана подсветка «правильных», разбор ошибок нейтральным тоном, `focusAreas` со ссылками на материал.

**Закон Хика и целевые размеры (Fitts).** Чем больше вариантов на экране и мельче цели, тем медленнее и ошибочнее выбор. → Вариант ответа — крупная кликабельная карточка на всю ширину (минимум 48 px по высоте), а не мелкий radio-кружок. Клик по всей области карточки, а не по кружку.

**Цвет несёт смысл только вместе с формой.** ~8% мужчин имеют нарушения цветовосприятия. → Все состояния навигатора продублированы иконкой/формой/толщиной рамки. Контраст текста не ниже 4.5:1, крупного — 3:1.

### 6.2. Дизайн-система

Замени текущие `:root`-переменные на полноценные токены (один файл `src/styles/tokens.css`):

- **Цвет.** Основной фон — тёплый нейтральный (не чисто белый: `#faf9f7`-типа), поверхности — белые с мягкой тенью. Акцент — спокойный сине-зелёный или индиго средней насыщенности, один. Семантические цвета (успех/ошибка) — только на странице результата и в админке, приглушённые, не «сигнальные». Категории получают собственные пастельные акценты (`categories.color`) — они помогают ориентироваться в блоках, но должны быть тише основного акцента.
- **Типографика.** Шкала из 6 ступеней (12/14/16/20/26/34), базовый размер текста вопроса — не меньше 20 px, `line-height` 1.5–1.6. Системный шрифтовой стек оставь (нет внешних загрузок — проект работает в закрытом контуре).
- **Ритм.** Единая шкала отступов 4/8/12/16/24/32/48. Радиусы: 8 (мелкое), 12 (карточки), 16 (крупные панели). Тени — двухслойные и мягкие, не «карточка парит».
- **Движение.** Переходы 150–250 мс, `ease-out`. Анимируются только `opacity` и `transform`. Обязательно `@media (prefers-reduced-motion: reduce)` — отключает всё.
- **Тёмная тема** — по `prefers-color-scheme`, через переопределение токенов. Тесты часто проходят вечером.

### 6.3. Экраны

- **Главная (`/`)** — вместо списка тестов: короткое объяснение, из каких блоков состоит тест и сколько примерно вопросов, карточки категорий с числом вопросов и подготовительными ссылками, одна крупная кнопка «Пройти тест». Форма ФИО + команда — на этом же экране или шагом после, без лишней страницы.
- **Прохождение (`/attempt/:id`)** — двухколоночный layout на десктопе (вопрос + навигатор справа), одноколоночный на мобайле со сворачиваемым навигатором. Плашка категории над вопросом. Крупные карточки-варианты. Кнопки навигации внизу, «Завершить» — визуально отдельно от «Далее», чтобы не нажать случайно.
- **Результат** — по п. 4 и 5: tier-заголовок, балл, сообщение, «На что посмотреть» с категориями и ссылками, свёрнутый разбор.
- **Админка** — плотнее и информативнее пользовательской части (у админа другая задача — сканировать данные): компактные таблицы, липкие заголовки, фильтры в одну строку, читаемые числа (моноширинные цифры, `font-variant-numeric: tabular-nums`).
- **Состояния** — обязательны и оформлены: загрузка (скелетоны, не спиннер на пустом экране), пустое состояние с подсказкой что сделать, ошибка с кнопкой «Повторить».
- **Адаптив** — от 360 px. На мобайле вопрос и варианты занимают экран целиком, навигация — крупными кнопками внизу в зоне большого пальца.
- **Доступность** — семантические теги, `fieldset`/`legend` для вариантов, видимый фокус, навигация с клавиатуры целиком, `aria-live` на смене вопроса и на прогрессе.

## 7. Тесты (обязательно)

Backend, JUnit:
1. Парсер — существующие тесты не ломаются; добавь кейс с привязкой к категории.
2. Сборка попытки: берётся `n` из `[min, max]` по каждой категории; при нехватке вопросов берутся все; категории без вопросов пропускаются; вопросы не повторяются внутри попытки; при полном отсутствии вопросов — `409`.
3. Тайминги: накопленное время перезаписывается, а не суммируется при повторной отправке; отрицательное значение → 0; превышение потолка обрезается; сумма таймингов больше длительности попытки → `timing_suspicious`.
4. Метрики: расчёт самого долгого/быстрого вопроса, отсечка по `min-samples`, медиана, агрегаты по категориям, исключение незавершённых и подозрительных попыток.
5. Правила фидбэка: границы порогов (49/50/74/75/89/90), формирование `focusAreas`.
6. Безопасность контракта: ни `GET /api/attempts/{id}`, ни `PUT .../answers/{qid}` не возвращают правильный ответ.

Frontend: как минимум smoke-проверка, что автосейв вызывается при выборе ответа и что таймер паузится по `visibilitychange` (если тестового рантайма нет — не тащи его ради этого, но опиши в README, как проверить руками).

## 8. Критерии приёмки

1. `docker-compose up --build` поднимает всё с нуля; миграции применяются на чистой БД.
2. Загрузка MD-файла без категории отклоняется с понятной ошибкой; с выбором существующей — вопросы добавляются в неё; с созданием новой — категория появляется в списке.
3. «Пройти тест» собирает попытку из 10–15 вопросов **каждой** непустой категории; два запуска подряд дают разные наборы.
4. На экране один вопрос; переход к любому вопросу через навигатор работает; ответ сохраняется сразу; перезагрузка страницы возвращает попытку в том же составе и с теми же ответами.
5. Время на вопрос пишется в БД, суммируется при возвратах и не растёт, пока вкладка неактивна.
6. `GET /api/admin/metrics` отдаёт самые долгие и самые быстрые вопросы, среднее и медиану времени на вопрос и разбивку по категориям; дашборд их рисует; при нехватке данных показывает честное «недостаточно данных», а не нули.
7. Страница результата: верные ответы не подсвечены, по умолчанию видны только ошибки, есть tier-сообщение и `focusAreas` со ссылками.
8. UI: клавиатурная навигация проходит весь флоу, контраст проходит проверку, `prefers-reduced-motion` отключает анимации, вёрстка держится на 360 px.
9. `mvn test` зелёный. README описывает категории, алгоритм сборки, настройки выборки, метрики времени и деструктивность миграции `V3`.

## 9. Порядок работы

Перед реализацией покажи: (1) новые миграции, (2) изменённые и новые контракты API (DTO), (3) список файлов, которые создаёшь и меняешь. Затем иди по порядку: backend (категории → сборка попытки → тайминги → метрики → фидбэк) → frontend (пошаговое прохождение → результат → админка) → дизайн-слой → README и тесты. Каждый шаг оставляет проект в компилирующемся состоянии.
