# Промт для разработки: «Платформа для тестирования знаний»

Ты — senior full-stack инженер. Разработай production-ready проект **«Платформа для тестирования знаний сотрудников»** целиком, от структуры репозитория до рабочего `docker-compose up`. Пиши весь код, конфиги, миграции и README. Не оставляй TODO и заглушек — всё должно компилироваться и запускаться.

## 0. Технологический стек (строго)

- **Backend:** Java 17, Spring Boot 3.2.x, Maven. Зависимости: Spring Web, Spring Data JPA, PostgreSQL driver, Bean Validation (`spring-boot-starter-validation`), Flyway (`flyway-core` + `flyway-database-postgresql`). Никаких Micrometer/Actuator-метрик, Lombok — по желанию.
- **Frontend:** React 18 + Vite, React Router. UI-библиотеки НЕ использовать — только собственные компоненты и обычный CSS (можно один общий `styles.css` или CSS-модули). Для HTTP — нативный `fetch`.
- **БД:** PostgreSQL 16.
- **Контейнеризация:** Docker + docker-compose, три сервиса: `postgres`, `backend`, `frontend`. Именованный volume для данных Postgres. Проект поднимается одной командой `docker-compose up --build`.

## 1. Принятые решения по «открытым вопросам» (реши именно так)

1. **Отображение вопросов:** все вопросы на одной странице (single-page прохождение), внизу кнопка «Завершить тест».
2. **Лимит времени:** без жёсткого лимита. Но backend фиксирует `started_at` и `finished_at` для расчёта длительности.
3. **Защита админки:** простой пароль через env-переменную `ADMIN_PASSWORD`. Все админ-эндпоинты требуют заголовок `X-Admin-Password`; при несовпадении — `401`. Фронтенд-админка спрашивает пароль один раз и хранит его в `sessionStorage`.
4. **Несколько тестов:** поддержка нескольких тестов одновременно. У каждого теста свой `id`, публичная страница `/test/:id`.
5. **Подготовительные ссылки:** привязаны к конкретному тесту (таблица `prep_links` с FK на `tests`). Задаются при загрузке теста или редактируются отдельным эндпоинтом.
6. **Повторное прохождение:** разрешено без ограничений. Каждая попытка — отдельная запись в `attempts`; в метриках считаются все попытки.

## 3. Схема БД (PostgreSQL, через Flyway-миграцию)

Все таблицы создаются миграцией `V1__init.sql`. Используй `BIGSERIAL`/`BIGINT` PK, `TIMESTAMPTZ` для времени, FK с `ON DELETE CASCADE` где логично.

- **tests** — `id`, `title`, `description`, `created_at`.
- **questions** — `id`, `test_id (FK)`, `number` (номер вопроса в тесте, целое), `text`, `correct_option` (`CHAR`, хранить кириллическую букву А/Б/В/Г). Уникальность `(test_id, number)`.
- **question_options** — `id`, `question_id (FK)`, `option_letter` (А/Б/В/Г), `text`. Уникальность `(question_id, option_letter)`.
  - *(Вместо отдельной таблицы `answer_keys` правильный ответ хранится прямо в `questions.correct_option` — это нормализованнее и проще для подсчёта. Если по ТЗ нужна именно таблица `answer_keys` — заведи её как `(id, question_id, correct_option)` 1:1, но опиши в README, что это дублирует поле.)*
- **prep_links** — `id`, `test_id (FK)`, `title`, `url`, `sort_order`.
- **attempts** — `id`, `test_id (FK)`, `first_name`, `last_name`, `team`, `ip_address`, `user_agent`, `started_at`, `finished_at (nullable)`, `status` (`IN_PROGRESS` | `COMPLETED`), `correct_count`, `total_questions`, `score_percent`.
- **attempt_answers** — `id`, `attempt_id (FK)`, `question_id (FK)`, `selected_option` (nullable — вопрос мог остаться без ответа), `is_correct` (boolean).
- **metrics** — таблица агрегатов по тестам: `id`, `test_id (FK, unique)`, `starts_count`, `completed_count`, `abandoned_count`, `total_duration_seconds`, `updated_at`. Инкрементируется атомарно при старте/завершении попытки (upsert). Дашборд читает и это, и агрегаты по попыткам напрямую — см. §5.

Добавь индексы: `attempts(test_id)`, `attempts(team)`, `attempt_answers(attempt_id)`.

## 4. Парсер единого MD-файла — это самая сложная часть, опиши явно

Вход: один `.md` файл (multipart upload). Файл состоит из **секции вопросов** и **секции ключа ответов**, разделённых строкой `---`, за которой идёт заголовок `## Ключ ответов`.

### 4.1. Парсинг вопросов
- Вопрос начинается со строки вида `**N. Текст вопроса?**` — число, точка, текст, всё обёрнуто в `**...**`. Извлекай `number` (целое) и `text`. Текст вопроса может содержать `?`, `«»`, спецсимволы, латиницу и кириллицу.
- Следом идут строки-варианты формата `- Б) текст варианта`. Буква варианта — **кириллическая** (А, Б, В, Г; допусти также Д, Е на случай 5–6 вариантов — не хардкодь ровно 4). Регулярка на вариант: строка, начинающаяся с `-` (или `*`), затем буква, затем `)`.
- Варианты относятся к последнему прочитанному вопросу. Новый `**N. ...**` начинает новый вопрос.
- Секция вопросов заканчивается на первом `---`, после которого идёт `## Ключ ответов` (не обрывай на `---` внутри текста, если он есть; ориентир — именно связка `---` + заголовок ключа).

### 4.2. Парсинг ключа ответов
- Найди заголовок `## Ключ ответов`, ниже — markdown-таблицу.
- Пропусти строку-заголовок таблицы (`| № | Ответ | ... |`) и строку-разделитель (`|---|---|...|`).
- Каждую строку данных разбей по `|`, отбрось пустые крайние ячейки. Получишь плоский список ячеек. **Иди по ячейкам парами** `(номер, ответ)`: в одной строке может быть 2, 3, 4 и более пар — обрабатывай ВСЕ пары, не только первую. Количество пар определяй динамически по числу ячеек, не хардкодь «4 пары».
- Для каждой пары: `номер` → целое, `ответ` → кириллическая буква. Собери карту `number -> correct_option`.
- Игнорируй пустые/битые ячейки (например, если в последней строке пар меньше) — не падай.

### 4.3. Связывание и валидация
- Свяжи вопросы с ключом по `number`, проставь `correct_option`.
- Валидация при загрузке (верни осмысленный `400` с описанием, а не `500`):
  - есть хотя бы один вопрос;
  - у каждого вопроса найден ключ; если для вопроса нет ответа в ключе — отклони с перечислением «осиротевших» номеров;
  - если в ключе есть номер, которого нет среди вопросов — предупреждение в ответе (не критично, но перечисли);
  - если `correct_option` вопроса не входит в набор его вариантов — ошибка.
- Название теста: бери из параметра запроса `title` (обязателен) либо из первого заголовка `# ...` файла, если параметр не передан.

### 4.4. Тесты на парсер (обязательно)
Напиши JUnit-тесты, используя `sample-test.md`, покрывающие: несколько пар в строке, неполную последнюю строку ключа, вопрос без ответа в ключе, вопрос с 4 вариантами. Также юнит-тест на подсчёт баллов.

## 5. REST API (префикс `/api`)

Опиши и реализуй эти эндпоинты. Ответы — JSON. Ошибки — единый формат `{ "error": "...", "details": [...] }` через `@RestControllerAdvice`.

**Публичные:**
- `GET /api/tests` — список тестов `[{id, title, description, questionCount}]`.
- `GET /api/tests/{id}` — тест с подготовительными ссылками и вопросами **без правильных ответов** (варианты отдаются, `correct_option` НЕ отдаётся, чтобы нельзя было подсмотреть из фронта).
- `POST /api/tests/{id}/attempts/start` — тело `{firstName, lastName, team}`. Backend берёт IP (учитывая `X-Forwarded-For`, т.к. за nginx) и `User-Agent` из заголовков. Создаёт `attempt` со `status=IN_PROGRESS`, инкрементит `metrics.starts_count`. Возвращает `{attemptId, startedAt}`.
- `POST /api/attempts/{attemptId}/submit` — тело `{answers: [{questionId, selectedOption}], }`. Backend подсчитывает правильные, пишет `attempt_answers`, ставит `status=COMPLETED`, `finished_at`, `correct_count`, `score_percent`, обновляет `metrics` (completed_count, total_duration_seconds). Возвращает результат `{correctCount, totalQuestions, scorePercent, details:[{questionId, number, selectedOption, correctOption, isCorrect}]}`.

**Админские (заголовок `X-Admin-Password`):**
- `POST /api/admin/tests` — multipart: `file` (MD), `title`, опционально `prepLinks` (JSON-массив `{title,url}`). Парсит и сохраняет тест. Возвращает созданный тест + отчёт парсера (сколько вопросов, предупреждения).
- `GET /api/admin/tests` — список тестов с полной статистикой.
- `PUT /api/admin/tests/{id}/prep-links` — заменить набор подготовительных ссылок.
- `GET /api/admin/attempts?testId=&team=` — список попыток с фильтрами (оба опциональны), пагинация.
- `GET /api/admin/attempts/{id}` — детализация попытки (все ответы, правильные/неправильные, время).
- `GET /api/admin/metrics?testId=` — агрегированные метрики (см. ниже). Без `testId` — по всем тестам.

## 6. Метрики (вручную, из PostgreSQL, без внешних систем)

Эндпоинт `GET /api/admin/metrics` возвращает JSON:
```json
{
  "testId": 1,
  "startsCount": 120,
  "completedCount": 98,
  "abandonedCount": 22,
  "averageDurationSeconds": 415,
  "scoreDistribution": { "0-20": 3, "21-40": 10, "41-60": 25, "61-80": 40, "81-100": 20 },
  "teamActivity": [ { "team": "Alpha", "attempts": 30, "avgScore": 72.5 } ]
}
```
- `startsCount / completedCount / abandonedCount` — из таблицы `metrics` (или считай агрегатами `COUNT` по `attempts` по `status`; выбери один источник истины и опиши в README). `abandoned = starts - completed`.
- `averageDurationSeconds` — среднее `finished_at - started_at` по COMPLETED.
- `scoreDistribution` — гистограмма по бакетам процента, считается SQL-запросом (`GROUP BY` по диапазону).
- `teamActivity` — `GROUP BY team`.
Дашборд на фронте рисует эти данные простыми HTML/CSS-барами (без chart-библиотек).

## 7. Frontend — страницы и маршруты

- `/` — список тестов (карточки, ссылка на прохождение).
- `/test/:id` — стартовая: описание, **подготовительные ссылки**, форма (имя, фамилия, команда) → кнопка «Начать».
- `/test/:id/run` — все вопросы на одной странице, выбор варианта (radio), кнопка «Завершить». Перед стартом дергает `start`, при завершении — `submit`.
- `/test/:id/result` — результат: балл, процент, детализация (что выбрано / что правильно).
- `/admin` — вход по паролю (форма → `sessionStorage`), затем: список тестов, форма загрузки MD-файла + ссылок, список попыток с фильтрами по тесту/команде, детализация попытки, страница-дашборд метрик.

Компоненты дели по папкам, выноси api-вызовы в `src/api/`. Обрабатывай состояния загрузки/ошибок.

## 8. Docker / инфраструктура

- `docker-compose.yml`: `postgres` (образ `postgres:16`, env из `.env`, named volume `pgdata:/var/lib/postgresql/data`, healthcheck), `backend` (`depends_on` postgres healthy, env для datasource и `ADMIN_PASSWORD`), `frontend` (билд Vite, отдача через nginx, проксирование `/api` на backend).
- Backend читает конфиг из env (`SPRING_DATASOURCE_URL/USERNAME/PASSWORD`, `ADMIN_PASSWORD`), Flyway применяет миграции на старте.
- `.env.example` со всеми переменными и дефолтами.
- Данные Postgres переживают перезапуск (проверяемо: `docker-compose down && up` — тесты остаются).

## 9. Критерии приёмки (по ним себя проверь)

1. `docker-compose up --build` поднимает всё; фронт доступен, API отвечает.
2. Через админку загружается `sample-test.md`, парсер корректно извлекает все вопросы и ВСЕ пары ключа из каждой строки таблицы (включая неполную последнюю строку).
3. Прохождение без авторизации: вводятся ФИО/команда, фиксируются IP и User-Agent, балл считается на backend, попытка и детализация сохраняются.
4. Админка: список тестов, список попыток с фильтрами, детализация.
5. `/api/admin/metrics` отдаёт все пять групп метрик из БД; дашборд их рисует.
6. Данные Postgres сохраняются между перезапусками.
7. Юнит-тесты на парсер и подсчёт баллов проходят.
